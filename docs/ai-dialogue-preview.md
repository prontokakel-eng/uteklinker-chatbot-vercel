# Preview conversation pilot

An area reply such as `30M2` used to fail the gibberish gate, and natural corrections missed a fixed preference grammar. Many FAQ misses returned contact text before invoking the model. Changing the model alone did not change those routes.

`AI_DIALOGUE_ENABLED=true` activates the new controller **only when VERCEL_ENV=preview**. A confident exact/fuzzy approved FAQ answer remains a direct response only without conversation history and without a refinement request. Once a conversation exists the model owns the turn, including apparent standalone questions, and can use approved FAQ as evidence. This deliberately trades some additional model calls for contextual intent without another phrasing classifier. Otherwise the model sees bounded dialogue and can call approved FAQ search, public website search or catalog discovery. It can ask clarifying questions, explain general concepts, and request alternative product formats. Product links and sizes are rendered by the existing verified catalog adapter, not invented by the model. The legacy route remains available by removing the flag.

## Safety and limits

- Blacklist, long/repetitive input and per-IP limits run first. Bounded numeric replies in an existing conversation may receive topic context for the gibberish check; this does not authorize facts or skip the remaining gates.
- Warranty, compensation, current commerce, support hours and structural sizing keep their existing dedicated routes. No messages are sent to staff.
- Source IDs, locations, dates, review status and content hashes stay on the server. AI/cache data and prior assistant replies cannot become approved source rows. Client-supplied source IDs are never used.
- Website search reads only robots/sitemap-approved HTTPS pages on the existing shop allowlist. It reads at most two candidate pages and bounded static paragraphs. It excludes commercial/warranty paragraphs and never flattens variant specification tables. R ratings use the existing exact-identity/all-variants adapter.
- Model-selected colour/appearance is resolved against published catalog controls. Alternative sizes keep the selected colour/look. No unrestricted browsing or arbitrary URLs, POST parameters, credentials or cookies are supplied by the model.
- Maximum three generation attempts plus at most two semantic review calls, two read-only tool calls, 4,000 total output tokens including reasoning and reserved failed-request allowances, no SDK retries, and a shared 26-second controller deadline. Each generation reserves at least 800 tokens for a separate review call. At most one draft revision is permitted across warranty repair and semantic feedback; a revised reply must pass review again. At most one transient timeout/connection retry may use the remaining attempts/time/budget; the full allowance of a failed request is reserved because it may be billed. Sol uses low reasoning; each response must complete. Truncated output is not shown as a successful answer.
- The UI retains up to 32 messages, including FAQ, website, AI, product, greeting and contact replies, with up to 2,400 characters each. Preview server history has the same per-message/count limit plus a fixed 24,000-character total budget, retaining complete recent messages. Legacy server routing still bounds its own history to six. Long conversations may require clarification when old details leave the window. Public source labels are untrusted hints only: the server re-retrieves up to four currently approved FAQ rows for earlier FAQ questions; it never promotes old assistant prose or client metadata to evidence. No private source IDs are sent to the browser. Other previous facts require fresh tool evidence.
- Telemetry contains response/model IDs, completion state and token counts, never questions, source content or credentials. Preview diagnostics compares a fixed synthetic legacy request with the bounded controller and is rate-limited. It cannot conclusively identify an earlier failure unless reproduced.
- Generated prose, including contact drafts, receives a separate semantic review call before release. The checker sees the customer question/history, proposed reply and current server-approved source rows. It considers unsupported qualitative/numeric facts, exact product/property scope, corrected preferences, reversed drainage, premature handoffs and unsafe sizing requests. Product claims require supporting verbatim quotations from source IDs the writer actually cited; code validates that quotes occur in the cited current row. A draft labelled sourced cannot bypass this requirement by receiving an evidence-free review verdict. General explanations and numbered lists do not require product evidence. This is a probabilistic additional model assessment, not proof that every assertion is correct or independent human review. Same-model correlated errors remain possible. AI_REVIEW stays pending. Direct FAQ, verified website/catalog adapters and pre-model policy routes are unchanged.

## Simplifying draft validation

The Preview controller no longer classifies product names from capitalization, property-word families or generic-intent word lists. It also no longer treats every digit in general prose as a product specification. The separate semantic check handles these meanings; ratings and numerical claims are evaluated for meaning and source support, rather than mere presence of a digit or R label. Source approval, source IDs, output shape, warranty/commercial restrictions, safe URLs and hard time/token/tool budgets remain server-controlled. Legacy production drainage checking remains separate and unchanged.

A rejected draft receives fixed server-written policy feedback and at most one revision inside the remaining budget. Invalid, missing, timed-out or repeatedly rejected reviews return contact text; unchecked candidate prose is never shown. A valid reviewed contact draft retains its explanation rather than always being replaced with generic text. No staff message is sent. Tests mock reviewer decisions to verify these control-flow boundaries; only live model evaluation can assess semantic decisions. Extra model latency and token use must be checked before production release.
